# Аутентификация: серверные сессии и граница «публичное/защищённое»

## Контекст

Backend был демо-режимом с одним захардкоженным пользователем (`CURRENT_USER_ID = 1`)
и без авторизации. Вводим настоящую многопользовательность: регистрацию, вход и
изоляцию данных между организаторами. Проект учебный, но пишем «как в прод».

## Решение

**Серверные сессии, а не JWT.** Id сессии хранится в SQLite (`express-session` +
`better-sqlite3-session-store`, тот же движок БД, что и остальной backend), клиенту
уходит только подписанная `httpOnly`-cookie (`sameSite: 'lax'`, `secure` по `NODE_ENV`,
rolling-срок 7 дней).

**Вход по email + паролю** (bcrypt, cost 10–12). Самостоятельная регистрация
(`POST /auth/register`) с явным `username` и автосозданием дефолтного расписания.
`email` и `username` — уникальны (409 при конфликте).

**Два актора, две зоны доступа:**

- *Публичные* (без сессии): `register`, `login`, публичный просмотр организатора и его
  открытых событий (`GET /public/{username}[/{slug}]`), `GET /slots`, `POST /bookings`,
  а также `GET /bookings/{uid}`, `cancel`, `reschedule` — attendee управляет своей бронью
  по ссылке, защита через неугадываемый `uid`.
- *Защищённые* (сессия организатора): весь `/event-types`, весь `/availability`,
  `GET /bookings` (дашборд), `confirm`, `reject`, `GET/PATCH /me`.

**Семантика отказов:** нет сессии на защищённом маршруте → **401**; чужой owner-scoped
ресурс → **404** (не раскрываем существование, отдельный 403 не заводим). `confirm`/`reject`
дополнительно проверяют `booking.organizerId === session.userId`.

## Следствия

- `cancel`/`reschedule` намеренно доступны анониму по `uid` — это не дыра, а модель
  Cal.com (attendee отменяет встречу по ссылке из письма).
- Раскрытие «пользователь уже существует» при регистрации допускает user enumeration —
  принято осознанно ради UX учебного проекта.
- Появляются новые публичные endpoint'ы `GET /public/{username}[/{slug}]`, которых нет
  в текущей TypeSpec-спеке, — их нужно добавить в контракт.
